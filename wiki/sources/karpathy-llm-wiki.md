# LLM Wiki (Karpathy 아이디어 파일)

**한 줄 요약**: 질문할 때마다 원문을 다시 뒤지는 [[rag]] 대신, LLM이 소스를 읽을 때마다 마크다운 위키를 점진적으로 쌓고 유지하게 하자는 제안. 이 저장소가 그 구현이다.

## 핵심 내용

- **문제의식**: RAG·NotebookLM·ChatGPT 파일 업로드는 매 질문마다 지식을 새로 찾아 조립한다. 쌓이는 것이 없다.
- **제안**: LLM이 구조화·상호링크된 마크다운 위키를 **지속적으로 유지**한다. 새 소스가 들어오면 요약을 쓰고, 엔티티·개념 페이지를 고치고, 모순을 표시하고, 종합을 갱신한다. → [[llm-wiki-pattern]]
- **분업**: 사람은 소스 선별·탐색·질문, LLM은 요약·교차참조·정리·기록. "Obsidian은 IDE, LLM은 프로그래머, 위키는 코드베이스." → [[obsidian]]
- **3계층 구조**: 불변의 원본 소스 / LLM이 소유한 위키 / 규칙을 정하는 스키마(CLAUDE.md 등). → [[wiki-schema]]
- **3가지 작업**: [[ingest]](소스 1개가 10~15개 페이지에 영향), [[query]](좋은 답은 위키에 다시 저장), [[lint]](모순·낡은 주장·고아 페이지·누락된 링크 점검).
- **두 개의 특수 파일**: `index.md`(내용 중심 카탈로그, 질의 시 먼저 읽음)와 `log.md`(시간순 append-only 기록, `## [날짜] 작업 | 제목` 접두어로 grep 가능). 소스 ~100개·페이지 수백 개 규모까지는 임베딩 기반 RAG 없이 index만으로 충분하다고 본다.
- **도구**: 규모가 커지면 로컬 검색 엔진 필요 → [[qmd]] 추천. Obsidian Web Clipper, 이미지 로컬 저장, 그래프 뷰, Marp 슬라이드, Dataview, git 버전관리.
- **왜 되는가**: 위키가 버려지는 이유는 읽기·생각이 아니라 **장부 정리(bookkeeping)** 비용. LLM은 지루해하지 않고 한 번에 15개 파일을 고친다. 유지 비용이 0에 가까워진다.
- **역사적 맥락**: Vannevar Bush의 [[memex]](1945) — 개인적·큐레이션된 지식 저장소와 문서 간 연상 경로. Bush가 풀지 못한 "누가 유지하나"를 LLM이 해결한다.

## 주목할 주장

- "지식은 한 번 컴파일되고 *최신 상태로 유지*된다. 매 질의마다 다시 도출되지 않는다."
- 문서는 의도적으로 추상적이며, 구체 구현은 각자의 도메인에 맞춰 LLM과 함께 정하라고 한다.

## 검토 의견 (Claude)

강점:
- RAG의 "축적 없음" 문제를 정확히 짚는다. 질의 결과를 위키에 되돌려 저장하는 루프가 핵심 차별점.
- 인프라 없이 마크다운 + git + 에이전트만으로 시작 가능. 진입 비용이 매우 낮다.

주의할 점 (추론):
- **오류 누적 위험**: LLM이 쓴 요약이 다음 요약의 근거가 되면 환각이 위키에 굳을 수 있다. → 모든 주장에 source 링크를 달고, raw는 불변으로 두어 언제든 원문 대조가 가능하게 해야 한다. 이 저장소 스키마에 반영함.
- **규모 한계**: index.md 방식은 수백 페이지를 넘으면 컨텍스트를 많이 먹는다. 그때 [[qmd]] 같은 검색 도구로 넘어가야 한다.
- **사람의 검토가 핵심**: 저자도 소스를 하나씩 넣으며 직접 검토하는 방식을 선호한다. 일괄 처리는 품질이 떨어질 수 있다.
- **비용**: 소스 1개당 10~15개 페이지 수정은 토큰 사용량이 적지 않다.
